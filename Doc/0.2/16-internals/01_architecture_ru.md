# Архитектура: как фреймворк устроен внутри

Эта страница объясняет модель, на которой построено всё остальное. Читать её не обязательно,
чтобы собрать окно из готовых компонентов, но обязательно, если вы пишете свой компонент,
ловите странное поведение или упёрлись в производительность.

## Immediate mode: дерево живёт один кадр

Привычный (retained) интерфейс — это долгоживущие объекты: вы создали кнопку, положили её в
панель, и она там лежит. Изменили данные — надо не забыть позвать `button.SetText(...)`,
иначе на экране останется старое.

Здесь наоборот. **Каждый кадр вы заново описываете, как интерфейс должен выглядеть прямо сейчас,
исходя из текущих данных.** Дерево элементов строится, используется и выбрасывается. Рассинхрона
«данные изменились, а на экране старое» не бывает в принципе: на экране всегда то, что вы
описали в этом кадре.

Отсюда главное следствие: **синхронизировать интерфейс с данными не нужно, потому что нечему
рассинхронизироваться.** Никаких подписок на изменения, никаких «обнови меня».

## Три фазы кадра

Каждый элемент проходит три фазы, всегда в этом порядке:

```
Measure  →  Arrange  →  Emit
```

**`Measure(available, ctx)` — «сколько тебе нужно места?»**
Элемент считает свой желаемый размер (`Desired`) и, если у него есть дети, спрашивает их о том
же. Идёт снизу вверх: чтобы узнать размер панели, надо сначала узнать размеры её содержимого.
`available` — сколько места предлагают; элемент вправе попросить меньше или больше.

**`Arrange(finalRect, ctx)` — «вот твоё место, разложи детей»**
Родитель уже решил, какой прямоугольник кому достался. Элемент запоминает его в `Bounds` и
раздаёт места детям. Идёт сверху вниз: место можно делить, только зная, сколько его всего.

**`Emit(list, ctx)` — «нарисуйся»**
Элемент добавляет в `DrawList` команды отрисовки (фон, бордюр, текст, картинка) и здесь же
обрабатывает ввод — клики и наведение. Ввод живёт именно тут не случайно: только на этой фазе
известны окончательные `Bounds`, а значит, и попал ли курсор в элемент.

Почему два прохода вместо одного? Потому что размер зависит от содержимого, а положение — от
размера. Один проход не смог бы отцентрировать элемент, ещё не зная его ширины.

## Где живёт состояние: ID-store

Раз дерево умирает каждый кадр, встаёт вопрос: где хранить позицию скролла, текст в поле ввода,
раскрытые ветви дерева? В самих элементах нельзя — они не переживут кадр.

Такое состояние живёт в **ID-store** (`UiState`) — хранилище «по стабильному ключу»:

```csharp
public sealed class MyState : WidgetState
{
    public float Scroll;
}

MyState st = ctx.State.GetOrCreate(ctx.State.MakeId(Key) + "/my", () => new MyState());
```

Ключ (`Key`) обязан быть **стабильным между кадрами** — по нему состояние и находится. Если ключ
меняется, фреймворк каждый кадр видит «новый» виджет с чистым состоянием: скролл прыгает в
начало, поле ввода теряет курсор, hover не срабатывает.

**Важно: данные мода в ID-store не хранятся.** Там лежит только внутренняя механика виджета.
Список колонистов, выбранный предмет, текст, который вы редактируете, — это ваши данные, они
живут у вас. Фреймворк их не копирует и не кэширует, поэтому «реактивность» достаётся бесплатно:
вы изменили свой список — следующий кадр нарисует новый.

## Ядро и адаптер

Код разделён швом на две части:

| Слой | Папки | Зависимости |
|------|-------|-------------|
| Ядро | `Core`, `Layout`, `Styling`, `Rendering`, `Elements`, `Components`, `Animation` | чистый C#, без Unity |
| Адаптер | `Adapter` | `UnityEngine` + `Verse` |

Ядро **ничего не знает про игру**: оно не рисует, а описывает, что нужно нарисовать, — складывает
в `DrawList` команды вида «прямоугольник с таким стилем», «текст в такой рамке». Адаптер эти
команды исполняет через `Widgets`/`GUI` и заодно поставляет ядру платформенные мелочи: измерение
текста (`ITextMeasurer`), размеры спрайтов (`ISpriteMetrics`), время, ввод.

Практический вывод для вас: **компонент пишется в ядре и Unity не трогает**. Если в компоненте
понадобился `UnityEngine`, почти наверняка что-то делается не на своём слое.

## Стили и темы

У каждого элемента есть собственный `Style` — то, что задали вы. Но большинство полей вы не
задаёте, и тогда они берутся из **слота темы** — именованного набора значений по умолчанию
(`"button"`, `"input/frame"`, `"orgchart/node"`). Слияние своего стиля со слотом даёт
**резолвнутый стиль**, доступный внутри компонента как `RS`.

Правило простое: **заданное вами всегда побеждает тему**, а незаданное берётся из темы. Поэтому
смена темы перекрашивает интерфейс целиком, но не затирает то, что вы указали явно.

## Что из этого следует для производительности

Дерево строится каждый кадр — около 60 раз в секунду. Всё, что вы делаете в коде построения,
делается 60 раз в секунду.

**Так делать не надо:**

```csharp
// ПЛОХО: список строится заново каждый кадр
var items = new List<string>();
foreach (Pawn p in map.mapPawns.FreeColonists)
    items.Add(p.LabelShort);
listBox.Items = items;
```

Это 60 новых списков в секунду и 60 обходов колонии — работа ради результата, который почти
всегда тот же самый.

**Так надо:**

```csharp
// ХОРОШО: список живёт у вас, перестраивается когда РЕАЛЬНО изменился
if (_colonistsDirty)
{
    _items.Clear();
    foreach (Pawn p in map.mapPawns.FreeColonists) _items.Add(p.LabelShort);
    _colonistsDirty = false;
}
```

**Для живых значений — делегат, а не копия.** Компоненты принимают `Func<T>`: значение читается
в момент отрисовки, само, и всегда актуальное.

```csharp
// ХОРОШО: прогресс читается из ваших данных каждый кадр, копию обновлять не нужно
new ProgressBar(() => job.Progress);

// ХОРОШО: поле ввода показывает ваше значение и сообщает об изменениях
new InputText { Value = () => settings.Name, OnChange = v => settings.Name = v };
```

**Тяжёлое — не в кадр.** Поиск по всем вещам карты, чтение файла, разбор XML в коде построения
интерфейса — это тот же поиск 60 раз в секунду. Считайте заранее, кэшируйте, инвалидируйте по
событию.

**Отдельно про `Events.Hover`.** Он стреляет каждый кадр, пока курсор над элементом, — в отличие
от `HoverEnter`/`HoverLeave`, которые срабатывают по разу на переход. Тяжёлый обработчик в
`Hover` просаживает FPS; если нужна работа «при наведении», делайте её в `HoverEnter`.

## Чего в модели нет

Полезно знать заранее, чтобы не искать:

- **Нет «перерисовать элемент X».** Перерисовывается весь кадр целиком, всегда.
- **Нет обратных ссылок «ребёнок → родитель».** Дерево обходится сверху вниз.
- **Нет событий изменения данных.** Данные читаются заново каждый кадр — уведомлять не о чем.
- **Нет позиций до `Arrange`.** До второй фазы `Bounds` бессмысленны: спрашивать координаты в
  `Measure` бесполезно, их ещё не существует.
